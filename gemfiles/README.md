# gemfiles/

One `Gemfile` per supported Rails minor version (see the "Supported versions"
table in the [README](../README.md)). The CI `gem` job
(`.github/workflows/ci.yml`) runs the suite against each one, selecting the
file via `BUNDLE_GEMFILE`, crossed with every supported Ruby version.

The `.gemfile.lock` files in this directory are **not versioned** (they are
gitignored). Ruby does change which transitive dependency versions get
resolved: for example, dev/test-only gems like `rubocop` pull in dependencies
(`parallel`, etc.) whose minimum Ruby floor rises over time. A `.lock`
generated with one Ruby version can pin a dependency version that is not
installable on an older Ruby we also claim to support — and since
`ruby/setup-ruby` runs `bundle install` in `deployment` mode whenever it
finds a committed lock, that mode forbids re-resolving, so the install fails
instead of silently downgrading.

That is why each matrix cell (Ruby × Rails) resolves its own lock on the fly,
never inheriting one generated by a different Ruby. `bundler-cache: true`
still caches `vendor/bundle` between runs, using that generated lock as part
of the cache key.

## Adding a new Rails version to the matrix

1. Create `gemfiles/rails_X_Y.gemfile` copying the structure of an existing one.
2. Run `BUNDLE_GEMFILE=gemfiles/rails_X_Y.gemfile bundle install` locally to
   confirm it resolves without conflicts (the `.lock` it generates is only
   for the local check — do not commit it).
3. Add `rails_X_Y` to the `rails:` matrix in `.github/workflows/ci.yml`.
4. Update the "Supported versions" table in the README and the upper bound in
   `trane.gemspec` if applicable.
